## 建议目标

为验证开发人员提供一条可重复执行的路径：准备协议与环境描述、DUT 源码和连接、必要的业务逻辑，生成包含 knob 接入的 UVMF 验证工程；完成编译后，通过各运行目录的 knob.cfg 调整预留参数并获得可核对的验证结果。

用户已纠正推进顺序：**先考虑 UVMF 如何接入公共验证框架，再开展具体项目试点**。此前选择的 `chi_async_bridge` 保留为后续候选试点，已完成的独立快照作为历史准备保留，当前不推进其基线运行、迁移或改造。原项目不得受实验影响的约束继续有效。隔离准备见 [CHI 试点隔离记录](phase2-chi-pilot-isolation.md)，顺序决定记录于 `knob-r2g`。

## 当前先形成的接入设计

下一份设计应独立于具体 DUT，回答以下问题。表中方向均为建议，尚未批准为接口或部署合同。

| 设计问题 | 建议评估方向 | 需要得到的结论 |
| --- | --- | --- |
| UVMF 的采用范围 | 核查生成器、基础库、生成工程及扩展机制；区分生成阶段和编译运行阶段的依赖 | 采用哪些部分，公共层需要补充什么，哪些内容仍由项目维护 |
| 项目接入合同 | 描述项目提供的接口/环境信息、DUT 连接、协议行为、参考模型和检查逻辑 | 开发者需要写哪些输入和代码，公共框架交付哪些文件和入口 |
| 代码所有权与再生成 | 优先评估保持上游独立、通过适配层接入；明确生成区与手写区 | 升级或再次生成时，如何保留业务代码和 knob 接入；扩展点须按选定版本核查 |
| knob 配置生命周期 | 分开结构描述、组件配置和运行参数，确定声明汇总、加载冻结及应用位置 | 哪个入口负责准备，何时首次读取，默认值和随机化如何避免覆盖 |
| 部署与版本 | 评估公共依赖的固定版本、项目锁定、独立环境、缓存及编译运行入口 | 新项目怎样部署，已有项目怎样继续使用旧版本，如何重建和回退 |

官方概述将 UVMF 定位为可复用 UVM 方法学和代码生成器；bench 生成课程还区分描述输入和生成后需要修改的内容。因此，本阶段先核查完整接入流程及手写代码边界，再确定自己的封装。[官方概述](https://verificationacademy.com/topics/uvm-universal-verification-methodology/uvmf/uvm-framework/)、[Bench Code Generation](https://verificationacademy.com/topics/uvm-universal-verification-methodology/uvmf/uvm-framework/bench-code-generation/)。公开课程摘要不证明具体发行版的扩展接口或 VCS 兼容性。

产出应包含职责边界、输入/输出、生命周期、目录与版本管理建议，以及需实测的问题。先以独立最小环境核查关键假设，再用真实项目检验方案；不从 CHI 的现有脚本、类层次或协议细节反推公共接口。

「快速部署」以步骤可重复、依赖明确、人工修改位置可列举、结果可核对来衡量。可行性验证后记录实际耗时和人工步骤，不预设未经实测的分钟数承诺。

## 组件分工与输入边界

| 部分 | 建议职责 | 需要明确的边界 |
| --- | --- | --- |
| UVMF | 根据结构描述生成验证环境基础代码 | 使用选定发行版实际支持的输入和扩展方式 |
| knob | 声明、校验、冻结并读取运行期配置 | 继续使用文件、整数/布尔和显式原生 seed 合同 |
| 集成与部署工具 | 准备依赖、调用生成器、连接配置、提供编译运行入口、归档结果 | 工具负责流程，不自动理解任意 DUT 的功能 |
| 验证开发人员 | 提供 DUT、连接信息、协议行为、参考模型和检查规则 | 框架生成不等同于业务验证已完成 |

结构描述和仿真参数分开管理。改变接口、连接、结构或编译期参数通常需要重新生成和编译；改变已经显式接入的 knob 值只影响下一次运行。部署入口可以接收目录、工具位置和原生 seed，不因此引入命令行 knob 值覆盖。

## P1 必须回答的技术问题

1. **工具链兼容性**：选定 UVMF 的源码、生成物和编译入口能否在 VCS W-2024.09-SP1 / UVM 1.2 下工作？需要哪些适配？不以官方概述或其他仿真器成功代替本机实测。
2. **配置生命周期**：相关 UVMF 字段何时首次使用？knob 能否在此之前汇总全部声明并冻结？不能直接假定沿用现有示例的 end_of_elaboration 加载时机。
3. **接入方式**：优先评估扩展类、组合或生成器公开扩展位置；若必须修改生成器或运行库，记录维护成本与替代方案后再决定。
4. **再次生成**：输入更新后，生成器如何处理手写代码？应明确分离或保留机制，并通过实际再生成检验。
5. **依赖与来源**：确认发行包来源、版本、运行库、Python 版本及生成器依赖；Python 工具按项目约定使用 uv 管理。若需要分发第三方内容，先核对发行包的许可和分发条件。

P1 的产物是可行性证据和设计结论。可行性代码不自动成为生产实现。若当前 VCS 组合无法支持目标流程，应回到范围评审，明确适配代价；不自动切换仿真器或扩大兼容承诺。

## 建议的最终验收场景

| 场景 | 可观察的通过依据 |
| --- | --- |
| 新目录首次部署 | 按记录的输入和依赖生成工程，完成编译与有自动检查的仿真 |
| 一次编译、多配置运行 | 改变发包数量、约束边界或布尔开关后行为符合预期，simv 及共享库哈希不变 |
| 同 seed 重放 | 固定产物、环境、配置、输入和随机化过程，事务与检查结果一致 |
| 配置错误 | 未知键、范围错误及业务规则冲突产生指定诊断；可提前发现的错误在激励前失败 |
| 检查逻辑确实有效 | 人为制造一个确定的 DUT 输出错误，自动检查能报告失败 |
| 重新生成 | 已有用户业务代码与 knob 接入保持有效，重新编译后回归通过 |
| 跨位置复用 | 相同参数组绑定不同位置后独立生效，同位置重复使用保持一致 |
| 结果分层 | UVM_FATAL/raw=0 仍被判为用例失败；原始非零码独立记录为运行异常 |
| 跨项目接入 | 两个具有代表性差异的项目使用相同公共版本，业务差异通过项目配置、协议组件和扩展代码表达 |
| 升级与回退 | 项目 A 升级不改变项目 B 的锁定版本；回退后可按原输入重放，版本与生成物均可追溯 |

当前第一阶段的 100 个 VCS 场景及 16 个脚本判定场景是框架基线，不能作为 UVMF 集成已经通过的证据。第二阶段当前没有 UVMF 生成、编译或功能实测结果。

## 面向所有设计项目的设计议题

以下是建议，尚未成为已批准的架构决定。

| 议题 | 建议原则 | 需要验证或确认的内容 |
| --- | --- | --- |
| 公共层与项目层 | 公共层维护 UVMF 集成、knob、通用协议组件和部署工具；项目层维护 DUT、连接、参考模型和业务检查 | 哪些既有资产进入公共库，哪些属于项目扩展；公共代码与项目私有代码如何分离 |
| 版本与部署 | 公共版本不可变，各项目显式锁定所用版本；版本升级由项目选择 | 分发方式、离线缓存、依赖清单、升级与回退方法；避免共享目录被原地更新后影响全部项目 |
| 生成与手写代码 | 生成区与用户代码区有明确边界，重复生成可检查 | 选定 UVMF 版本的扩展点、保留机制及差异处理，不能假定生成器天然保留所有修改 |
| 配置所有权 | 结构配置、UVM 组件配置、knob 运行参数各有明确职责与赋值顺序 | 取值阶段、类型转换、默认值来源、命名规范和冲突规则；避免同一字段被多个入口静默覆盖 |
| 工具链和复现 | 先固定一个经过验证的工具组合；Python 依赖由 uv 管理 | 生成器、运行库、编译器、模板、knob 及项目输入的版本记录；不把开发机路径写进交付工程 |
| 验证资产复用 | 通过两个有差异的项目检验公共接口；按实际需要规划 IP 到子系统的复用 | active/passive 使用、参考模型和检查逻辑边界，实际范围由试点决定 |
| 发布与回归 | 公共版本发布前运行框架和代表性项目回归，记录兼容矩阵及已知限制 | 许可证可用的执行节点、失败日志、编译产物及事务证据；历史通过不等同于新版本通过 |
| 维护与推广 | 维护者负责公共版本，项目负责人决定升级；新项目和存量项目分批接入 | 首批试点、支持边界、问题归属，以及是否需要单独的平台仓库；不先行迁移现有 knob 仓库 |

UVMF 官方培训明确包含生成代码后补充协议细节、连接 DUT 和实现参考模型的工作。因此，公共框架能够统一流程与复用资产，项目特有的功能正确性仍需由项目验证逻辑定义。[Siemens 官方课程说明](https://training.plm.automation.siemens.com/ilt/iltdescription.cfm?pID=303572________EDA__2023.2_1252)

## 建议首版控制的范围

首版建议固定一个 UVMF 版本和已有 VCS/UVM 组合，在接入设计明确后，以独立最小环境核查生成、接入、运行、检查和再生成的全过程。小 DUT 或官方示例只用于回答明确的技术问题，不作为提前选择项目架构的依据；真实项目试点随后开展。

首版建议暂不承担任意已有 UVMF 工程自动迁移、多协议 VIP 库建设、任意 DUT 自动生成参考模型或检查器，以及多仿真器适配。第一阶段关于无热更新、无命令行 knob 覆盖、显式接入、整数/布尔和原生 seed 的合同继续保留。

## 本轮待确认

- **已确认的推进顺序。** 先设计 UVMF 公共接入，再验证技术假设，最后开展项目试点。CHI 快照保留，当前不推进；隔离约束继续有效。
- **当前待明确的采用范围。** UVMF 在公共方案中承担哪些职责，项目通过哪些输入与扩展代码接入，已有验证资产如何复用。
- **后续待明确的交付标准。** 建议交付可重复部署、可编译运行并带自动检查的公共方案与示例，具体支持边界待设计核查后确认；不承诺自动推导 DUT 检查逻辑。

本轮确认路线图和上述顶层范围后，进入 P0 的详细访谈与 P1 所需的资料核查。详细输入格式、具体 DUT、可调参数、命令界面和再生成策略再按依赖逐轮确定，避免用尚未验证的实现假设提前约束用户。
