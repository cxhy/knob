## 第一轮：描述输入、工程维护与起步结果

### Q9：DV 用什么描述新环境

是否接受填写我们提供的 UVMF 原生 YAML 模板，描述接口信号、事务字段和 agent 关系，另用少量工程配置指定 RTL 文件清单与顶层？还是希望填写我们定义的简化描述，由工具转换成 UVMF 输入？

推荐：首版采用带注释和示例的 UVMF 原生 YAML 模板，加少量工程配置。封装生成入口和输入检查，保留官方描述能力，减少额外转换层的维护。具体字段、文件划分和命令尚未确定。

用户回答：采纳原生 YAML 模板加少量工程配置，同时强调必须考虑未来升级方向，未来需要为常见模块提供常见场景。首版的输入和扩展设计须为这些场景模板保留接入空间。具体场景清单、模板格式和扩展机制尚未确定；这不要求立即建设完整模板库，也不改变 Q5/Q6 中低优先级演进和 DV 自由增减的约定。

### Q10：生成后的工程怎样维护

新增接口或事务字段后，是否需要继续使用生成器更新工程？另一种方式是只生成初始工程，此后由 DV 完全手工维护。

推荐：以持续再生成为默认使用方式，明确业务代码的保留位置，优先采用独立手写文件和必要的 custom 区块。任意位置的手工修改不能自动承诺保留；具体扩展机制和冲突处理将在维护方式确认后继续讨论和核查。

已知依据：独立评估证明相同 YAML 再生成保留 60 个 HDL 文件，同时确认旧教程在 custom 区块外增加的 include 会被覆盖。这不证明修改 YAML 或跨版本升级也能无条件保留行为。

用户回答：持续再生成。按此确定工程维护方式；具体自动保留范围、冲突处理和扩展位置继续讨论，不把任意手改都能无损合并当作已确认或已验证能力。

### Q11：业务逻辑未补齐时，起步工程应怎样报告结果

DV 只填写接口描述、尚未实现协议驱动或参考模型时，是否允许先执行骨架编译和基础冒烟？还是要求业务逻辑补齐后才允许运行？

推荐：允许先检查工程结构和基础连通性，但明确报告这属于骨架检查；缺少业务激励或检查器时提示待完成部分，不能据此报告功能验证通过。具体检测方法和输出格式尚未设计，不能承诺自动判断任意业务实现是否完整。

用户回答：采纳。允许骨架编译和基础冒烟，明确未完成业务验证；功能通过必须有实际激励和检查依据。具体如何登记未完成项及报告状态仍待设计，不承诺自动判断任意业务实现是否完整。

## 第二轮：工程边界、再生成冲突与模板扩展

### Q12：验证工程怎样引用 RTL

框架是否可以要求调整设计项目的 RTL 目录？还是仅约定验证工程自己的目录，并引用项目已有的 RTL 文件清单？

推荐：只约定验证工程内部结构，通过文件清单引用 RTL；不复制或接管 RTL，不要求设计项目重排目录。验证工程可放在设计仓库内，也可位于独立目录；具体路径写法和可移植性规则后续收敛。

用户回答：直接引用设计提供的 filelist。RTL 编译输入以设计侧清单为准，验证工程负责接入该清单。具体相对路径基准、环境变量及编译选项的处理规则仍需在工具入口设计中核对；不据此声称任意现有 filelist 已验证可用。

### Q13：再生成遇到冲突时怎样处理

例如新骨架无法对应某个旧 custom 区块，或发现未纳入保留规则的手工改动，应如何更新现有工程？

推荐：能够明确识别的业务代码按约定保留；出现无法自动处理的情况时，保留现有工程，提供候选结果和冲突说明，由 DV 处理后再更新。该建议是待确认的行为要求，不代表已经实现了自动冲突检测或任意代码合并。

用户回答：由 DV 修复冲突，冲突在构建验证框架时很常见。将冲突作为正常的工程维护情形，修复判断属于 DV；不把所有冲突都能自动解决设为框架能力要求。候选结果、备份和诊断的具体实现尚未确定，不把上一轮推荐的完整操作流程都视为用户逐项批准。

### Q14：常见场景模板由谁扩展

未来增加常见模块或业务场景模板时，是否允许 DV 在项目侧自行添加，并由团队逐步整理为共享模板？还是必须由框架维护者修改核心并发布后才能使用？

推荐：提供项目侧和团队侧的模板扩展入口，新增场景模板无需修改框架核心，由项目显式选择使用。首版先明确扩展边界，不提前建设完整场景库；模板格式、发现规则和版本分发仍待后续设计。

用户回答：是，项目和团队自行扩展场景模板是框架增长的必经之路。保留项目侧与团队侧的扩展入口，新增模板无需修改框架核心，并允许逐步积累为共享模板。具体模板格式、发现方式与发布版本策略继续设计。

## 第三轮：首版自动化边界

### Q15：首版是否自动解析 RTL 并连接 DUT

生成工程时，是否需要读取 RTL 端口并自动完成 DUT 连线？还是由生成器准备 interface/BFM 和连接位置，再由 DV 填写 DUT 实例及端口连接？

原推荐（未采纳）：首版生成 interface/BFM 骨架、基础时钟/复位模板和明确的 DUT 连接位置，具体 DUT 实例及连线由 DV 补充。常见模块模板以后可预置已知连接；通用 RTL 解析与自动连线暂不纳入首版。此题细化 Q8 中 DV 提供接口连接信息的职责，不改变业务行为由 DV 负责的边界。

用户回答：RTL 解析调用其 `hdl-kragph` MCP，根据设计交付的相关文档进行连线。因此接入方案需要纳入该解析工具和文档驱动的连线过程，不能继续把首版完全手写 DUT 连线作为既定范围。后续独立接入记录已确认实际名称为 `hdl-kgraph`，注册及最小 stdio 查询结果见 [输入核查](hdl-mcp-input-inspection.md)；当前会话加载和真实工程能力不能据此自动视为已验证。不会用其他工具替代用户指定工具，也不把解析到端口等同于已经理解协议连接语义。

### Q16：可选 knob 接入自动化到什么程度

首版是否提供可选 knob 接入模板与示例，由 DV 显式声明和应用可调参数？还是需要进一步支持在 YAML 中标记参数，再自动生成相应 knob 声明与接入代码？

推荐：先提供可选 knob 接入模板、统一初始化位置和典型参数示例，DV 显式声明可调项并在使用处应用；从 YAML 批量生成 knob 接入代码留作后续扩展。普通 UVMF 工程独立可用的约定不变。具体生命周期接入点需结合 UVMF 配置随机化顺序核查，不在此预先固定回调或承诺兼容所有初始化时机。

用户回答：可以，采纳可选 knob 初始化模板和典型参数示例，由 DV 显式声明与应用可调项；YAML 批量生成 knob 接入代码留作后续扩展。无 knob 的独立工程能力保持不变。具体生命周期接入点仍需核查。

## 第四轮：连线结果维护与不确定信息

### Q17：自动连线结果如何保留和修改

是否将自动推导的端口连接保存为可编辑映射，由 DV 修订，并作为后续再生成的依据？还是每次重新读取文档推导连线？

推荐：保存可编辑的连线映射及其 RTL、设计文档来源，允许 DV 明确修订；输入变化后核对受影响的连接。映射的具体文件格式与生成代码的组织尚未确定，也不承诺自动解决版本变化引起的所有语义冲突。

用户回答：同意。保存可编辑的连线映射及 RTL、设计文档来源，允许 DV 修订并供后续再生成使用；输入变化后核对受影响连接。映射的文件格式仍由后续设计确定。

### Q18：缺失或冲突的连线信息如何处理

例如 RTL 与文档中的位宽、复位极性或接口用途不一致，或者文档未解释某个端口用途，应如何处理自动连线？

原推荐（责任人已由用户更正）：生成能够确定的部分，同时明确列出未解决项，交由 DV 补充或修正；不猜测语义或静默接常量。存在未解决的必需连接时，不将该结果标记为完整连线检查通过。具体诊断与检查机制待工具接口核查后设计。

用户回答：不一致应直接反馈给设计人员，文档由设计提供，问题由设计人员负责解决。设计交付文档与 RTL 的矛盾或信息缺口归设计侧澄清、修正，不把设计语义判断或设计交付修正责任转给 DV。此责任与 Q13 区分：验证工程再生成和手写代码的合并冲突仍由 DV 修复。这里确定的是反馈对象及处理职责，本轮没有向任何设计人员发送消息。
