# 第二阶段：公共依赖部署与版本管理访谈

日期：2026-11-11。关联 Beads：`knob-uv7.3`。状态：Q20～Q25 均已回答，公共部署原则已收敛；具体目录、命令和配置格式由后续实现设计确定。

承接 [接入访谈](phase2-integration-contract-interview.md)。用户要求先过完所有问题，生命周期 Q19 留到之后核对，不阻塞当前访谈。无 knob 独立可用、引用设计 filelist、持续再生成和 DV 扩展自由等既定要求不重问。

## Q20：公共依赖放在哪里

公共框架和 UVMF 是在团队公共位置安装多个版本，供项目引用，还是每个项目各自保存副本？

推荐：团队维护按版本区分的公共安装目录，项目记录所用版本及内容标识，通过配置定位安装目录。项目保存自己的 YAML、连线映射和业务代码；无 knob 工程无需引用 knob。具体物理路径及分发工具之后确定。

用户回答：采纳公共多版本安装与项目显式引用；公共依赖后续统一放在 workspace 中。具体子目录和部署入口尚未确定，本轮没有移动或安装依赖。

## Q21：公共版本如何升级

发布公共新版本后，已有项目是否自动跟随，还是由项目主动选择升级？

推荐：项目固定版本，新版不自动影响已有项目。DV 主动升级并执行受影响检查，旧版保留供回退；不通过可变 latest 路径隐式切换。此问题与依赖集中安装或项目自带副本均兼容。

用户回答：没问题，采纳项目固定版本、主动升级、保留旧版回退。

## Q22：首版工具支持范围

公共框架首版是否先支持当前已验证的 VCS W-2024.09-SP1 / UVM 1.2，还是同时必须支持其他仿真器？

推荐：首版承诺当前固定 VCS/UVM 组合，将工具路径和环境入口放在可配置的适配层，为其他工具预留扩展位置；当前不承诺其他仿真器已兼容。uv 管理 Python 的项目约定继续适用。具体部署命令和跨机器验证在后续明确。

用户回答：先按当前 VCS/UVM 组合推进；用户认为 VCS 和 UVM 高度向后兼容，兼容问题通常无需特别考虑。因此当前不扩展兼容矩阵或将假设性版本差异列为阻塞，实际遇到差异时处理。现有实测证据仍对应记录的工具版本；本轮未执行其他版本验证。

## Q23：部署入口提供到什么程度

DV 首次使用时，是否由公共入口带着完成工程初始化、生成、编译和运行，还是只提供脚本示例，由各项目自行组织命令？

推荐：提供统一入口，覆盖初始化、生成/再生成、单独编译、单次运行与回归，同时保留项目侧扩展入口。具体命令名由实现确定，不要求 DV 学习 UVMF 内部脚本；编译与运行分开，保持复用产物的能力。

## Q24：公共版本由谁维护

Q23 用户回答：采纳统一入口，覆盖初始化、生成/再生成、单独编译、单次运行和回归，并保留项目扩展入口。

项目需要临时修改公共框架或 UVMF 模板时，是否允许直接修改大家正在引用的公共版本，还是在项目扩展或新版本中处理？

推荐：已发布的公共版本保持不变。项目先通过自己的扩展处理差异，共性改进由框架维护者整理为新版本，再由各项目选择升级。无需为每个项目特殊需求修改公共核心。

## Q25：首版是否要求离线部署

Q24 用户回答：采纳已发布公共版本保持不变，项目差异通过扩展处理，共性改进由框架维护者形成新版本。

准备好 workspace 中的公共依赖后，新项目是否必须能在不联网下载依赖的环境中生成、编译和运行？

推荐：支持。公共依赖准备阶段集中取得并核对所需内容；项目日常使用不临时联网下载。Python 继续通过 uv 管理，具体依赖准备方式在实施时确定。

用户回答：采纳依赖集中准备后的离线使用要求。
